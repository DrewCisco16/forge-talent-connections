1Unchanged

Introduction

1.1 The problem this solves

When you ask one AI model to check its own work, it usually says the work is fine. It cannot reliably see its own blind spots. The obvious fix is to ask several models and compare. That fix works, but only under specific conditions — and it fails badly outside them. This manual specifies those conditions precisely so the tool is built to help rather than to feel helpful.

1.2 The single most important finding

Blind models alone make things worse

Kim et al. (2026) ran 260 controlled configurations with matched compute. Parallel models that never see each other's work and have no verifier amplified errors by 17.2×. The same models with a verifier that checks claims before combining them amplified errors by 4.4×. The verifier is the entire difference.

This is why the tool is not five models voting. It is five models proposing corrections, and a verification layer — part code, part you — deciding which corrections are real. Removing the verification layer converts a working system into the worst-performing design measured.

2Revised

Plain-Language Primer

2.1 The homework analogy

Imagine you wrote a report and want to catch every mistake before turning it in. You ask five friends to check it. Each reads it alone, without seeing what the others said. Then you collect all their notes.

The catch most people miss

If all five friends went to the same school and had the same teacher, they will tend to make the same mistakes. Five friends who all learned the same wrong thing will all miss the same error — and worse, they will all agree, which makes you feel more confident, not less.

This is exactly what happens with AI models. Kim, Garg, Peng, and Garg (2025) tested more than 350 models and found they agreed with each other 60% of the time when both were wrong. The stronger the models, the more their errors matched.

2.2 The fix: a calculator and a library card

Some things do not require an opinion at all. If a friend says "12 plus 35 equals 50," you do not need a vote. You need a calculator. If a friend says "this fact comes from this source," you do not need agreement. You need to look the source up.

The core idea of the whole tool

A calculator never makes the same mistake an AI makes. A library catalog never hallucinates a citation. These are deterministic gates. They are the most valuable part of the system because their errors are completely unrelated to the models' errors.

2.3 What the tool does, step by step

  1. It checks whether it should run at all. If one good model already handles this task class well, it tells you to skip the whole thing and save your money.
  2. It sends the work to five models. Each proposes corrections without seeing the others, and without seeing any earlier round's results.
  3. Every proposed correction is sorted. Can a machine check it? Math, citations, code tests, and data formats can be.
  4. Machine-checkable claims are checked by machine. Passed claims are accepted. Failed claims eliminate that answer. No AI opinion involved.
  5. Claims a machine cannot check — judgment, interpretation, framing — go into a short list for you. This is the only part that needs a human.
  6. It repeats with a different lens each round: five passes, four of which can eliminate. The fifth calibrates confidence and cannot rule anything out.
  7. It measures whether new errors are still being found, and it measures how much the five models disagreed. When the yield decays and your queue is empty, it stops.

You submit:  a 3-page market analysis, 14 citations, one revenue projection.

Read the last two lines again

The residual passed. The divergence passed. The run still does not stop, because fifteen judgment items are unworked. Under §6.3 the stop rule is a conjunction and the queue is part of it. A residual below tolerance is not permission to commit.

Model diversity is established as failing to decorrelate errors (Kim, Garg, Peng, & Garg, 2025). Whether method diversity — Inversion versus FMEA versus IDOV versus TRIZ — decorrelates is unknown. Mechanically your passes are prompts, and preprint evidence suggests prompting strategy has negligible effect on failure diversity. Test: compute error correlation separately for each pass. Flat across passes means the frameworks are cosmetic.

6Revised

The Math, Explained Simply

Five formulas run this system. Each is given plainly first, then formally.

6.1 Effective seat count — how many models you really have

Plain: if your models make the same mistakes, having five of them is like having one and a half. This tells you how many you effectively have.

n_eff = n / (1 + (n - 1) * rho)

  n   = number of seats
  rho = how similarly they fail (0 = totally different, 1 = identical)

  rho = 0.0  ->  5 seats behave like 5.00
  rho = 0.2  ->  5 seats behave like 2.78
  rho = 0.4  ->  5 seats behave like 1.92
  rho = 0.6  ->  5 seats behave like 1.47   <- observed regime
  rho = 0.8  ->  5 seats behave like 1.19
  rho = 1.0  ->  5 seats behave like 1.00
Why this matters for your wallet

At rho = 0.6, going from five seats to six moves effective seats from 1.47 to 1.51. You pay 20% more for a 3% gain. This formula is the argument for spending on deterministic gates instead of more models.

6.2 Capture-recapture — how many errors nobody caught

Plain: if lots of errors were spotted by only one model, the models are not seeing much of what is there, so more errors are probably still hiding. Same math biologists use to count fish in a lake.

N_hat = S_obs + (f1 * f1) / (2 * f2)

  S_obs = total distinct errors anyone found
  f1    = errors found by exactly ONE seat   (singletons)
  f2    = errors found by exactly TWO seats  (doubletons)
The uncomfortable double meaning

A high singleton count is exactly what "each model caught what the others missed" feels like from the inside. It is also the statistical signal that more errors remain uncaught. Your impression that the system is working and the evidence of residual risk are the same number.

New in 1.1 — the estimator goes silent exactly when you are most exposed

v1.0 said to report this as a lower bound. That is true but not sufficient, because the bound can be zero. Correlated seats catch the same things, which produces no singletons, which makes the estimator conclude nothing was missed.

6.3 The decay curve — when to stop

Plain: each pass finds fewer new problems than the one before. Fit that shrinking pattern to a curve, then use the curve to estimate how many problems are still out there.

Fit:        VCY_k = a * e^(-b * k)          for k = 1, 2, ... K
Remaining:  R_hat = a * e^(-b*(K+1)) / (1 - e^(-b))
Revised in 1.1 — two ambiguities that changed the answer

VCY means corrections, and a correction is a gate FAILURE. v1.0 defined VCY as "verified corrections found in round k" while its worked example fitted the curve to total claims proposed. Those are different series. A claim that passes the gate is a confirmation — the artifact was right. A claim that fails is a correction — a real defect was found. Only failures count. Fitting accepted claims makes a pass that found nothing look maximally productive and stops the residual from ever decaying.

k starts at 1, not 0. v1.0 left this unstated. On the same yields, zero-based indexing gives a = 11.76, R = 0.330 and one-based gives a = 26.94, R = 0.757 — a 2.3× difference in the number that decides whether you stop. At tolerance 0.5 the two indexings disagree about whether to commit. This manual specifies k = 1…K.

The stop rule is a conjunction, and the queue is part of it 
STOP only when ALL of these hold:

  1. b > 0                       yields are actually decaying
  2. R_hat < your tolerance      residual is acceptable
  3. judgment queue is EMPTY     every escalation worked
  4. singleton fraction below    your own calibrated alarm
     your threshold              (§9.2; you must set it)

A low residual is not permission to commit. §10 lists an unworked queue as a do-not-build condition, because unworked judgment claims are precisely the unverified-ensemble topology this system exists to avoid.

6.4 The 0.45 gate — should you run at all

Plain: measure how well one good model does on your task. If it already scores above about 45%, adding models will not help and will probably hurt. Run one model plus gates instead.

Re-estimate this threshold for your own work

0.45 comes from six agentic benchmarks in Kim et al. (2026). Their leave-one-domain-out R² was −2.09, meaning the model could not predict absolute performance in an unseen domain. Treat 0.45 as a starting prior and re-measure once you have 30+ scored tasks.

6.5 Seat divergence — is the panel actually a panel?

New in 1.1.

Plain: measure how much the five seats disagreed. On a hard problem they should. If they agree exactly, they are not five seats.

J(A,B) = |A intersect B| / |A union B|      per seat pair, per pass
divergence_k = mean of J over all pairs in pass k

  Claim sets are compared on CONTENT -- (kind, warrant) -- not on
  seat-assigned labels, so two seats phrasing the same finding
  differently register as agreement.
Unanimity is an alarm, not a result

On a non-trivial artifact, independent seats do not produce identical claim sets. If they do, they share a failure mode and the panel is worth roughly one effective seat. Raise a collapse flag and check rho before trusting anything the run produced.

Silence is not collapse

If every seat returns an empty claim set, the sets are trivially identical — but that is the marginal-yield signal (this pass found nothing), not a monoculture signal. Suppress the collapse flag when all seats are silent. A warning that fires on every empty pass is one operators learn to ignore.

7.1 Evidence that argues against this system

Recorded as fully as the supporting evidence, per the standing evidence protocol.

  • Overall mean multi-agent improvement across six benchmarks was 0.0%. The average system gains nothing; only correctly selected deployments gain.
  • On software engineering tasks, every multi-agent architecture underperformed a single agent, from −1.3% to −12.8%, because baselines exceeded 0.45.
  • Mixing model vendors did not help: heterogeneous configurations underperformed strong homogeneous ones by 12.6 percentage points.
  • Vaccaro et al. (2024) found human-AI combinations underperformed the better of human or AI alone (g = −0.23, p = .005) on decision tasks. Only augmentation of a human baseline was positive.
What this evidence permits you to claim

That a correctly-scoped, gate-verified, human-adjudicated pipeline reduces certain error classes on decomposable tasks with low single-agent baselines. It does not permit claiming that more models produce better answers in general. The evidence says the opposite.

8.2 Stage 1 — accounts and API keys

Revised in 1.1 — five seats, and what it costs you

v1.0 said "three is the recommended maximum" while §6.1's worked table assumed five. This version standardizes on five seats: four reached by outbound API key, plus one in-process.

Record what that overrides. Turn count scales as T = 2.72(n + 0.5)^1.724, so five seats sit past the knee of the curve, and per-seat reasoning capacity thins under a fixed budget. The preflight gate still returns 3 as its recommendation and nothing raises that cap silently — five is a deliberate operator decision, taken with the cost visible.

The in-process seat cannot be the orchestrator

The orchestrator is code, not a model, precisely so it can see everything while the seats see nothing. If the session running the orchestrator is also a seat, that seat can see gate verdicts — its errors then correlate with the adjudication itself, which is the exact failure blinding exists to prevent. Run it as a separate session or call with no visibility into orchestrator state. Otherwise you have four blind seats plus one that is not, and your rho is understated.

Key safety — non-negotiable

Never paste a key into a chat window, document, screenshot, or source file. Never commit .env. If a key is exposed, revoke it in the console immediately. A leaked key is someone else spending your money.

8.3 Stage 2 — install and wire the orchestrator

The single most common way this build fails

A resolver function that returns True by default. If your citation checker cannot reach the source, it must return False. A permissive resolver silently converts your verified system back into an unverified ensemble, and you will not notice. Probe it with an identifier that cannot exist and confirm it says no.

New in 1.1 — admissible evidence

Only scholarly articles, empirical data, technical manuals, and primary source literature may support a claim. DOIs, PMIDs, standards (ISO, IEC, IEEE, RFC, NIST, ASTM), ISBNs, and repository accessions are placed; a DOI minted by a data repository classifies as data, not as an article. Everything else is inadmissible — there is no permissive fallback branch. Preprints are a distinct class and are rejected by default; admitting one is an explicit opt-in that must be recorded in the audit trail.

Note that a citation must be both admissible in class and confirmed to resolve. Passing one check is not passing the other.

Daily Operating Procedure

Use this every time you run the tool. It should take under a minute to follow.

9.1 The run sequence

StepAction
1Confirm the task decomposes. If strictly sequential, stop and use one model.
2Confirm the task class baseline is still below your threshold.
3Submit the artifact. Let the five passes run, one at a time.
4Do NOT read the model outputs yet. Read the GATE RESULTS first.
5Work your escalation queue. These are the judgment items only you can decide.
6Check the residual estimate. Below tolerance?
7Check the singleton fraction and the per-pass divergence.
8Commit ONLY if the queue is empty AND the residual is below tolerance.
9Log the run. Add the outcome to your calibration set.
The discipline that makes this work

Read gate results before model prose. Gate results are facts; model prose is persuasion. Dell'Acqua et al. (2026) showed wrong answers from AI users were graded more coherent — reading the prose first is how a polished error gets committed.

10.1 Honest limitations of this manual

  • The 0.45 threshold comes from six agentic benchmarks and did not generalize across domains (leave-one-domain-out R² = −2.09). Re-estimate locally.
  • The decay-based stopping rule is standard in software inspection but has not been validated on LLM critique chains. Calibrate against your own data.
  • Whether framework diversity decorrelates errors (H9) is unresolved. If it does not, the multi-pass structure may be cosmetic.
  • Capture-recapture assumes independent detection, which is violated here. All residual estimates are lower bounds, and §6.2 shows the bound can be zero.
  • None of the cited studies tested this exact architecture. Every number is transferred from an adjacent design and should be re-measured.
  • New in 1.1: the divergence findings in §6.2 and §6.5 were measured against synthetic seats. They validate the machinery, not the behaviour of any real model.
